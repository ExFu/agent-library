# Principle: Concrete first, abstract later

## Why

Most users are not meta-cognitive thinkers. Architecture lectures before any action lands as noise. The user feels lost, the agent feels like it is performing, and the substrate does not get built. The user disengages.

Build first, name concepts second. The user feels progress, builds confidence by doing, and acquires the vocabulary when they hit it in practice. By the time the agent says the word "scope", the user is already working inside one and the term lands as a label for something they understand.

## How

Open the install conversation by asking the user to describe their world in concrete terms ("what organisations are you part of? what teams? what projects or clients are live right now?") and spin up the matching grouping folders and scope folders directly. The user sees folders appearing for things they recognise. They are doing the install with you, not being lectured at.

Introduce concepts (substrate, ontology, librarian, scope, convention) only when the user encounters them in practice. At that moment, the concept has a referent the user can point at, and explanation lands.

Use diagrams and structured explanations when the user reaches a calibration moment that benefits from them, not as opening curriculum. The substrate diagram is a clarification tool, not an introduction.

## What

Apply during: install conversations, first-time creation of any new ontology type for a user, teaching moments mid-session.

Avoid: opening the install with the substrate diagram (was the v0.2.x pattern; misfires). Asking "have you used a knowledge base before?" as the first question. Explaining the three-tier composition before the user has created anything.

When the user asks a meta question ("how does this work?"), then concrete-first relaxes: they are asking for the abstraction, give it. But do not volunteer it.
