# Migration: the actor record

Follows: exfu/20260903-1825/ontology.md#actors

## What changes and why

Before this change the library's actor was whatever `durable/ledger/install.md` said on its `installed by:` line, and the dispatcher fired a trigger only when that string equalled the trigger's `owner` string. A person has more than one name. The line held a display name ("Alastair"), the docket skill wrote the handle ("al") as owner, and the trigger was dropped in silence on every hourly run: due, armed, and never fired, with nothing anywhere saying so.

After this migration `durable/ledger/actors.md` holds one record per actor: a canonical handle as heading, and beneath it the display name, aliases, and the ids by which channels reach them (a Slack member id, an email address). Every tool resolves an owner or a channel target through that record before comparing, a trigger with no `owner` belongs to the library's actor, and the due view reports what it excluded and why instead of skipping quietly. `install.md` keeps its `installed by:` line as a display name; it is no longer an identity key.

## Preconditions

Applies when `durable/ledger/` exists and `actors.md` is not in it. A library installed at plugin 0.11.2 or later writes the record at install and gets `not-applicable`.

## Instructions

This migration writes one new file and asks the user two questions. It carries `requires_user_decision: true` because only they know the names they go by.

### 1. Gather what the library already knows

- The handle: an `actor handle:` line in `durable/ledger/install.md` if one was appended; else the `owner` most triggers across `*/docket/triggers.jsonl` carry, when it is short and lower-case; else first-name-lowercase from `user/context/about-me.md`.
- The display name: the `installed by:` line, and the name in `about-me.md`.
- Medium ids: the `target` of every `dm` channel in `user/docket/channels.jsonl` whose notes say it reaches the user themself, and the email in `about-me.md` if present.
- Every distinct `owner` value across the triggers that is not `any`. Each one is either the handle, an alias of the user, or another person; the user decides which.

### 2. Confirm with the user

Show what you found in two lines and ask, in plain words: "Your triggers will be owned by `al`. Any other names you go by that an agent might write down: first name, nickname, initials?" and, for each owner value that is not obviously theirs, "Is `<value>` you, or someone else?" A value that is someone else is left alone; it is theirs to register in their own library.

### 3. Write the record

Append to `durable/ledger/actors.md`, created from `${CLAUDE_PLUGIN_ROOT}/substrate/templates/durable/ledger/actors.md`, one record in the template's shape: the handle as heading, `display`, `aliases` (comma-separated, including every owner value the user confirmed as theirs), one line per medium id, and `recorded:` with the date, your surface and the plugin version.

### 4. Verify

Run the due view once and read its flags:

```
python3 ${CLAUDE_PLUGIN_ROOT}/scheduled-tasks/library-index/index.py due <substrate-root>
```

Every trigger the user confirmed as theirs should now appear either as due or as not yet due; none should be flagged as owned by an unregistered actor. If one still is, the alias is missing from the record: append it, do not edit the trigger.

## Success condition

`durable/ledger/actors.md` exists with one record whose heading is the handle; `explain` on any trigger the user owns prints an `owner:` line that resolves to that handle and raises no owner objection; the migration is recorded `applied` in `durable/ledger/migrations.md` with the handle and aliases the user confirmed.

## If something goes wrong

The migration writes one new file. Remove `durable/ledger/actors.md` and the tools fall back to `install.md` exactly as before. Record `failed` with what happened.
