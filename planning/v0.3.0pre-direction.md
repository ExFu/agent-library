# v0.3.0pre — Direction

Planning doc for the v0.3.0 plugin release. Captures the model evolution from v0.2.x (current shipped: v0.2.8) to v0.3.0.

Anchors to: `T1-overview.md` (project-wide goals), `v0.2.0-substrate-revision.md` (the prior structural decision, materially superseded here), `cross-cut-extension-and-wrapping.md` and `cross-cut-storage-architecture.md` (both need refresh, see below), `audit-skills-and-resources.md` (May 2026 audit — folded into the install-redesign workstream rather than running separately).

**Status:** direction agreed in conversation, May 2026. Not yet decomposed into T2 workstreams. Open architectural questions listed at the end.

---

## Why

The v0.2.0 work shipped a workable plugin and proved the substrate model in real engagements. Four problems have surfaced in real-world use that v0.2.x cannot fix incrementally; they need a deliberate revision.

**1. First-run UX fails for real humans.** The install agent has been over-coerced into running steps too literally. It motors through the script, leans on jargon before concepts have landed, and doesn't read the room when a user is lost. In the field, Al is having to hand-hold users through the install personally, often interrupting the agent to redirect it. The agent needs more agency to slow down, and the install needs to be concrete-first in practice, not just in principle.

**2. Structure isn't captured as proper conventions.** The substrate-guide carries a lot of careful design (HARD vs soft folder rules, naming, README discipline, two-layer PII model, fuzzy-zone test for scope vs context), but it's a 430-line narrative document that the user never sees and the agent loads as a single read. Conventions are not addressable atoms; they are paragraphs inside a guide.

**3. The current top-level shape is too rigid.** v0.2.0 forced `orgs/`, `teams/`, and `scopes/` as top-level siblings with `scopes/` flat ("ALL scopes top-level"). The rationale was "humans don't browse scope folders directly, Claude does." That premise is falsified by Al's own use of his own substrate, where he nests under `scopes/clients/<scope>/`. Real users want to organise their work areas in ways that make sense to them.

**4. There is no curation layer.** The substrate has one machine-walked artifact today (`_meta/substrate-index.md`) and no general mechanism for the substrate to look after itself. As substrates grow, drift accumulates: stale READMEs, orphan scopes, missing dependency links, accumulated inbox material that wants consolidating. Without a curation layer, the user is the only librarian.

A fifth thread (memory consolidation, deduplication, deep-vs-fresh distinction) is real but explicitly deferred. May land via third-party providers (Anthropic memory, vendor-supplied) rather than in-house. Not in v0.3.0 scope.

## How

### Principles

- **World-first install, concepts second.** Build the user's substrate as a byproduct of asking "what are you working on?" The agent surfaces concepts only when the user hits them in practice. Diagrams and explanations come as needed, not as opening curriculum. This is the existing "concrete first, abstract later" principle taken seriously in the implementation, not just stated in the skill body.
- **Conventions as primitives.** Named, addressable, atomic. Each convention is its own small file in a convention library. Skills and install entrypoints reference convention atoms by name instead of restating the same conventions inline. The substrate-guide becomes a narrative index over the atoms, not the source of truth.
- **Ontology as a meta-convention.** Folder *types* are themselves first-class. ExFu ships a base ontology (context, todos, sops, instructions, contacts, skills, librarians, conventions, ontologies, ...). The ontology is extensible. Each type has a defined shape and discovery rule.
- **Three-tier composition.** Every ontology type has three potential homes:
  - **ExFu-defined** at `<root>/exfu/...` (materialised at install from `${CLAUDE_PLUGIN_ROOT}`).
  - **User-defined** at `<root>/user/...` (the user's personal layer).
  - **Scope-defined** at `<root>/scopes/.../<scope>/...` (specific to one scope).

  Precedence is local-first: scope wins over user, user wins over ExFu. Resolution is the agent's job; the storage is just convention-typed folders at the relevant tier.
- **Type-folder discoverability.** A folder *named after* a type *is* one. Any folder named `librarians/` is a librarians folder. Any folder named `todos/` is a todos folder. The agent can discover all of one type with a name match.
- **Meta-recursion.** Ontologies are themselves an ontology type. So `ontologies/` folders can appear at any tier and extend or override the base ontology, including at scope level. The system describes itself in its own vocabulary.
- **Convention snapshots, not references.** When an ontology-typed folder is created (e.g. `todos/`), the relevant convention template (`agent.md`) is copied into that folder at creation time. The folder carries its own snapshot of the convention that governed its creation. Updates to the upstream template do not automatically rewrite past folders. The substrate is self-describing at creation time, not by distant reference.
- **Substrate is self-contained.** ExFu-shipped material (ontologies, conventions, librarians, base skills, templates) is materialised into `<root>/exfu/` at install. The plugin (`${CLAUDE_PLUGIN_ROOT}`) is the canonical source; the substrate carries its own copy. Substrates outlive plugin installs, move to new machines, and operate without the plugin if needed. Convention updates require an explicit refresh, not an implicit overwrite.
- **Sane defaults, not enforced shapes.** Conventions exist to help with *where* things go and to provide reasonable starting points. A scope (or the user) MAY use a completely custom approach for any given ontology type. ExFu may ship multiple default options for the same type (e.g. todos as a flat checklist or as structured records); the user picks one at folder creation, or rolls their own.
- **Self-orienting agent material.** Every artifact that another agent will read (this plan, skill bodies, convention atoms, `agent.md` per-folder snapshots, install instructions, librarian instructions, etc.) must be readable cold. The reader has no access to the conversation that produced it. Each file therefore carries enough Why and How that an agent can orient and act without external context. The Golden Circle (Why → How → What) is the recommended structure; the reasoning is as helpful as the conclusion, sometimes more so when the situation drifts from what the file anticipated.
- **Outcome-framed elicitation, not concept-framed.** When the install agent offers an ontology type to a user, the question is about the outcome the type provides, not the mechanism behind it. *"Do you want me to capture todos and tasks for this project?"* lands; *"do you need a todos folder?"* does not. *"If you had someone looking after this data for you and doing housekeeping at the end of each day, what would you ask them to do?"* lands; *"do you want a librarian function?"* does not. Each user-facing ontology type ships with an elicitation prompt in user vocabulary that the install agent uses during the conversation. Some ontology types are *infrastructure* (librarians, conventions, ontologies, schemas) and are typically not offered to the user at all; they're materialised silently from `<root>/exfu/`. The user-facing vs infrastructure split shapes what gets surfaced during install.
- **Principles as shipped material.** Reasoning patterns that improve agent behaviour (Golden Circle when explaining or reasoning, outcome-framed elicitation when asking users, concrete-first when introducing concepts, plain language with users, why-before-what when shaping AI behaviour, etc.) ship as a first-class ontology type at `<root>/exfu/principles/`. Each principle is its own atom. Runtime agents read them alongside the user's `wow` to absorb cross-cutting behavioural guidance that has proved useful in practice. Same discipline ExFu uses in its own planning, made available at runtime. User and scope tiers can extend or override.
- **Recommendations as shipped catalogue.** ExFu maintains a curated catalogue of third-party connectors, plugins, and skills that most users would benefit from considering. This ships as `<root>/exfu/recommendations/` (an ontology type). The install agent consults it when the user mentions a tool, workflow, or pattern that something already exists for, and surfaces relevant entries at the moment they are useful, not as a buffet at the start, and not as a passive resource the user has to know to ask about. The catalogue is open to user and scope extensions via the three-tier composition.
- **Portable skill-definitions.** Skills become an ontology type with a defined shape, not Claude-specific `.skill` packages. The definition carries enough information for an agent to render it into a target platform (Claude Code skill, Cowork skill, Gemini gem, etc.). ExFu's renderers handle the rendering; user-authored skill definitions are platform-neutral.
- **Librarians as the curation layer.** Background work that looks after the substrate is encoded as librarians. A single scheduled task fans out across all discoverable librarian folders. Each librarian is just instructions. ExFu ships a base set; users and wrappers add their own.
- **Agent-driven migration.** Migrating an existing v0.2.x substrate to v0.3.0 is the work of an agent that compares the user's current reality to the new model and reshapes interactively, not a pre-written script. The substrate-guide ships the new shape and the comparison contract; the agent does the work.
- **Memory deferred.** Memory consolidation (fresh-vs-deep, deduplication, timestamping, archival) is not in v0.3.0. May land later via third-party providers or a future librarian. The principle (memory is its own concern, possibly outsourced) is in scope; the implementation is not.

### Structural shape

Substrate root is ExFu-owned. Everything at root is either ExFu infrastructure (`CLAUDE.md`, `_meta/`, `_trash/`) or one of three reserved containers (`exfu/`, `user/`, `scopes/`):

```
<substrate-root>/
  CLAUDE.md
  _meta/
  _trash/
  exfu/                  # ExFu-delivered material, materialised at install
    ontologies/
    conventions/
    librarians/
    skills/
    templates/
    principles/          # agent-runtime principles (Golden Circle, etc.)
    recommendations/     # curated third-party catalogue (connectors, plugins)
  user/                  # the personal-tier scope
    scope.md
    README.md
    context/
    databases/
    scratch/
    [ontology-typed folders the user has adopted ...]
  scopes/                # work-area scopes
    [grouping-folders, arbitrarily nested ...]
      <scope-name>/
        scope.md
        README.md
        context/
        [ontology-typed folders this scope has adopted ...]
```

Each ontology-typed folder (e.g. `todos/`, `sops/`, `librarians/`) carries its own `agent.md` alongside its `README.md`. The `agent.md` is a copy of the convention template that was in force at creation time. The folder follows the convention captured in *its own* `agent.md`, not whatever the upstream template happens to say today.

Key rules:

- **`exfu/` is the materialised ExFu tier.** Holds `ontologies/`, `conventions/`, `librarians/`, `skills/`, `templates/`. Populated at install from `${CLAUDE_PLUGIN_ROOT}` and refreshed only on deliberate update. Not a scope (no `scope.md`). Owned by ExFu by convention; the user doesn't edit it directly.
- **`user/` is the personal-tier scope.** It is a scope by shape; it carries `scope.md` and `README.md`. It is named `user/` by reserved convention so the resolver always knows where the personal layer lives.
- **`scopes/` is a container, not a scope.** No `scope.md`. Arbitrary grouping folders may nest under it. Grouping folders carry only `README.md` (human-facing only); they are not scopes.
- **A scope folder is identified by `scope.md`.** The marker doubles as the scope's agent-facing reference. Find-all-scopes is a recursive search for `scope.md` files under `scopes/` (plus `user/scope.md` for the user-tier scope).
- **README.md for humans, `scope.md` for agents.** Every folder still has a README per the existing Purpose/Contents/Dependencies convention. Scope folders additionally have a `scope.md` that carries the scope's structured reference (entities, current work, conventions, dependencies on ontology atoms). The two cross-reference each other.
- **`agent.md` carries the convention snapshot for an ontology-typed folder.** When the agent creates a typed folder (e.g. `todos/`), it copies the relevant `agent.md` template from `<root>/exfu/conventions/<type>/agent.md` (or the user-tier equivalent if the user has overridden it) into the new folder. The folder thereafter follows its own copy. Upstream changes do not propagate automatically.
- **Ontology-typed folders may appear inside any scope** (user or work-area). The ontology declares the set of types; the scope adopts the ones it needs.
- **Scopes are not nested inside scopes.** Grouping folders can nest; scopes are leaves. If a scope wants children, it becomes a grouping folder and its previous content gets restructured. A librarian can flag drift and suggest restructure.

### Trade-offs being made

- **`orgs/` and `teams/` as top-level primitives go away.** They become grouping folders under `scopes/` (e.g. `scopes/teams/Sales/` for the team scope, `scopes/teams/Sales/projects/<project>/` for projects under that team). Org and team stop being special-cased. Multi-org and multi-team support drops out for free: it's just grouping folders.
- **Personal-default at substrate root (v0.2.0) moves under `user/` (v0.3.0).** Breaking change for existing substrates. Migration is agent-driven. v0.2.x users keep working until they choose to migrate.
- **Per-scope skills (`scope-<name>` Claude skills) die.** Their job (discoverability when a scope is mentioned) is taken over by `scope.md`. The agent walks scopes by file pattern when it needs to find one.
- **Single monolithic substrate-guide → atom library plus index.** The guide is recast as a narrative index over the conventions atoms. Source of truth moves to the atoms.
- **Skill artifacts go provider-agnostic at the definition layer.** Adds rendering as a step but unlocks cross-platform portability. Skill-packaging continues to exist as the Claude-specific renderer.
- **Three-tier composition adds resolution logic.** The agent needs to know how to resolve a request like "find me todos" across all three tiers. Modest cost; large gain in extensibility.
- **Convention by copy, plugin as source.** ExFu material lives canonically in the plugin; substrates carry a copy at `<root>/exfu/`, and each typed folder gets its own `agent.md` snapshot at creation time. Cost: install does more work; conventions can drift between substrates and across folders within the same substrate; refreshes need explicit user action. Benefit: substrates are self-contained (survive plugin removal, move cleanly between machines); folders evolve independently of upstream convention changes; the user owns when to adopt updates rather than waking up to a silently changed system.

## What — candidate T2 workstreams

Five parallelisable workstreams. Each gets its own T2 plan once this T1 is firm.

**T2-A — Substrate shape v6.** New folder shape, `user/` scope, scope marker file, three-tier composition rules, scope discovery via `scope.md` walks. Decides the migration agent's contract: what input it needs, what comparisons it makes, what it preserves. Supersedes the structural sections of `v0.2.0-substrate-revision.md`.

**T2-B — Conventions and ontology.** The named atom library. The base ontology (types and their schemas). For each ontology type: a schema, an `agent.md` template (the per-folder convention snapshot), and (for user-facing types) an elicitation prompt in outcome-framed user vocabulary that the install agent reaches for when offering the type. The schema format itself. The extension mechanism (`ontologies/` folders at any tier). The narrative index that replaces the monolithic substrate-guide. The materialisation step (plugin → `<root>/exfu/`) at install, and the refresh mechanism when ExFu publishes a new version. Decides which conventions are atoms vs which stay narrative. Decides the ontology schema language (JSON Schema, YAML, custom). Includes the starter ontology of grouping folders (`teams/`, `clients/`, `projects/`, `organisations/`) as sane defaults under `scopes/`. Includes two new ontology types beyond the structural ones: `principles/` (agent-runtime behavioural atoms such as Golden Circle, concrete-first, outcome-framed elicitation) and `recommendations/` (curated third-party catalogue of connectors, plugins, and skills the install agent surfaces in context). Determines the user-facing vs infrastructure split: user-facing types (todos, contacts, sops, databases, etc.) are offered during install with elicitation prompts; infrastructure types (librarians, conventions, ontologies, schemas, principles) are materialised silently and not offered. Recommendations sits in between: shipped silently, but actively consulted by the install conversation. Some types ship with multiple default-option variants (e.g. todos as flat checklist vs structured records); the elicitation prompt covers the variants.

**T2-C — Librarian framework.** The single daily scheduled task that fans out. The librarian-folder discovery rule. The contract a librarian's instructions must satisfy. The base librarians that ship with ExFu (substrate-index migrated; structure-suggestions; team-sync-and-conflict-detection as candidates). The three-tier discovery (plugin / user / scope librarians, all run together).

**T2-D — Install conversation redesign.** The world-first UX flip. Open by asking the user to describe their world in concrete terms ("what organisations are you part of? what teams? what projects or clients are live right now?") and spin up the matching grouping folders and scope folders directly, using ExFu's starter grouping-folder ontology as sane defaults. Introduce concepts (substrate, ontology, librarian, etc.) only when the user hits them in practice. Use Claude's inline UI elements (cards, images, structured choice surfaces) and `AskUserQuestion` where they reduce reliance on text walls; reach for them when offering choices rather than embedding multi-choice prompts in prose. For each user-facing ontology type, surface the elicitation prompt from T2-B in outcome-framed user vocabulary. Actively consult `<root>/exfu/recommendations/` and surface relevant entries when the user mentions a tool, workflow, or need that something already exists for (e.g. user mentions calendar work, install agent surfaces the calendar connector recommendation). Renames "substrate" and other insider vocabulary in user-facing surfaces. Updates all three install skills (solo, team, team-admin). Folds in the May 2026 audit's findings on trigger realism and description quality. Probably the most user-visible workstream.

**T2-E — Portable skill-definitions.** The provider-agnostic skill-definition shape. The renderer pattern (Claude-target renderer, Gemini-target renderer, etc.). What `setup-inbox`, `setup-reminders`, `setup-writing-styles` produce changes: today they generate `.skill` packages, tomorrow they generate skill-definitions that are then rendered. Includes the migration of existing per-user skills.

A sixth strand sits inside T2-B and may want to split out:

**(Possible T2-F — Plugin-internal restructure.)** The plugin itself currently ships `skills/`, `templates/`, `resources/`, `scheduled-tasks/`. Under the new model the plugin should ship `ontologies/`, `conventions/`, `librarians/`, `skills/`, `templates/`. The build pipeline (`plugin/build/build.sh`) needs to compose those into each variant. Either folded into T2-B (since the ontology lives there) or split out depending on size.

### Work shape

T2 work can run in parallel once cross-cut refreshes are firm. T2-A (shape) and T2-B (conventions/ontology) are the most upstream and probably want to settle first. T2-C, T2-D, and T2-E can begin in parallel once those are in draft.

T3 plans drop out of T2 when each workstream is detailed enough that an implementation agent can act. v0.3.0 won't ship from this T1 alone.

## What — deferred / out of scope

- **Memory consolidation.** Per-scope fresh-vs-deep memory, deduplication, archival, timestamping. May arrive via third-party providers (Anthropic memory, vendor-supplied) or a future librarian. The principle (memory is its own concern) is in scope; no implementation in v0.3.0.
- **Multi-platform skill rendering.** The skill-definition contract is in scope (T2-E). The renderers for non-Claude targets (Gemini gems, etc.) are out; they're a follow-on once the contract is stable.
- **Per-scope ontology extension.** Whether scopes can declare scope-local ontology extensions is open. Default for v0.3.0: ontology extension at user-tier only. Scope-local extension is a possibility once we see whether it's needed.
- **Wrapping-plugin composition mechanics.** The runtime composition of an ExFu wrapping plugin (acme-exfu, etc.) is still pending the open questions in `cross-cut-extension-and-wrapping.md`. v0.3.0 ships the principle and contract shape; concrete wrapping work is downstream.

## Open architectural questions

These need resolution before T2 work commits.

1. **Migration agent contract.** What does the migration agent know about a user's existing substrate? What's the input format (live filesystem walk, or a structured manifest the user generates)? What guarantees does it make (idempotence, partial-progress recovery, rollback)? How does it interact with `_meta/storage-backend.md` and the wow navigation map?
2. **Reserved names.** `exfu/`, `user/`, `scopes/`, `_meta/`, `_trash/`, and `CLAUDE.md` are reserved at substrate root. Are any other top-level names reserved? (Enforcement vs convention is handled in question 11.)
3. **Ontology schema format.** JSON Schema, YAML schema, or a custom convention? Each has trade-offs (JSON Schema is verbose but tooled; YAML schema is lighter but less standardised; custom is bespoke and rigid).
4. **Schema location.** Schemas for ontology types: shipped with the plugin only, or also writable by the user / scope when extending the ontology? Default leaning: schemas ship with the plugin; user/scope extensions carry their own schemas in their own `ontologies/<type>/schema.<ext>` shape.
5. ~~**Plugin-internal restructure.**~~ Resolved: the plugin stays flat in shape (`ontologies/`, `conventions/`, `librarians/`, `skills/`, `templates/` directly at plugin root) and is the canonical source. At install, the relevant material is materialised into `<root>/exfu/` with the same flat shape. The plugin doesn't need its own `user/`; the substrate carries that.
6. **Per-scope skills migration.** Existing v0.2.x users have `scope-<name>` skills. Do we deprecate them gracefully (the agent reads them but stops creating them), or migrate them into `scope.md` during the migration agent's pass?
7. **Versioning the substrate model itself.** The substrate-guide carries a `version:` line (currently v5). Does a v0.3.0 substrate carry an explicit substrate-model version somewhere (e.g. `_meta/substrate-version.md`) so the agent can detect what model it's working with? Useful for the migration agent.
8. **The `instructions/` ontology type.** Al mentioned "folder-specific instructions" as a distinct ontology type. Is this a separate type, or is it served by `scope.md` and per-folder READMEs already? Probably resolved by clear schemas in T2-B.
9. **The audit's recommended-rework order.** Whether the urgent fixes from `audit-skills-and-resources.md` (substrate triggers, exfu-upgrade-from-team-to-admin description, git-substrate-sync triggers) get patched into v0.2.x before v0.3.0 lands, or roll forward into v0.3.0's install redesign. Default leaning: roll forward, since the redesign will rewrite descriptions anyway. Caveat: if v0.3.0 timeline slips, patch the worst offenders into v0.2.x for the field.
10. **Convention refresh mechanism.** When ExFu publishes a new version of a convention, how does an existing substrate adopt it? Likely an explicit "refresh exfu" agent task that diffs the plugin's current shape against `<root>/exfu/` and asks the user about each change. Could be implemented as an ExFu-shipped librarian, but the deliberate-user-decision character feels more like a one-shot agent task (parallel to migration). Open: at what granularity refreshes happen (whole `exfu/` or per ontology type), and whether per-folder `agent.md` snapshots are touched (default leaning: no, folders are sovereign once created; the user opts in folder by folder if they want to upgrade).
11. **Reserved names enforcement.** Reserved names at root (`CLAUDE.md`, `_meta/`, `_trash/`, `exfu/`, `user/`, `scopes/`) are convention; reserved type-folder names (`librarians/`, `ontologies/`, `conventions/`, etc.) are also convention. Does the agent refuse to create folders that collide with reserved names, or just discourage them? Default leaning: discourage with a librarian check, don't enforce in the storage layer.
12. **User-facing vs infrastructure ontology types.** First-pass split: user-facing (offered during install with elicitation prompts) = scopes, context-for-me, todos, contacts, sops, instructions, databases. Infrastructure (materialised silently, not offered) = librarians, conventions, ontologies, templates, schemas, principles. The `skills` type sits ambiguously: skill *templates* are infrastructure but a *skill-definition the user authors* is user-facing. The `recommendations` type sits in a third category: shipped silently, but actively consulted by the install conversation. Resolved during T2-B as the catalogue is built. Affects how many things the install conversation surfaces and in what order.
13. **Boundary between principles, brand voice, and wow's always-on kernel.** All three carry agent behavioural guidance. Today: `cross-cut-brand-voice.md` carries the AI-slop banlist and tonal guidance; `wow-template.md`'s always-on kernel carries communication style and decision-making defaults; the proposed `principles/` ontology type would carry cross-cutting reasoning patterns (Golden Circle, outcome-framed elicitation, etc.). Risk of duplication and confused source-of-truth. Possible resolutions: (a) principles supersedes brand-voice-as-cross-cut, the cross-cut becomes one principle atom; (b) the three serve genuinely different purposes (principles = how to reason; brand voice = how to write; wow kernel = this user's specific preferences) and the boundary is just clearer documentation; (c) principles becomes the discoverable shipped layer, brand voice gets folded in, and wow's kernel stays per-user-only. Default leaning: (b), but worth re-litigating in T2-B.

## Provenance and how to read this plan

Authored by Alastair (ExFu founder) in conversation with Claude in May 2026, grounded in real-world experience of installing v0.2.8 with users. The four problems were observed in the field (Alastair hand-holds most installs himself); the structural model (three-tier composition, `user/` scope, scope marker, ontology as meta-convention, `agent.md` per typed folder, librarian framework) was developed iteratively across several rounds of conversation and represents Alastair's considered position, not a brainstorm.

An agent reading this cold should treat the **Why** as describing real observed problems, the **How** as a settled direction (decisions made, not options on the table), and the **What** as scaffolding for T2 work that hasn't started yet. The **Open architectural questions** are genuinely open and need resolution before the relevant T2 commits; question numbers that are struck through (`~~5~~`) have been resolved post-draft. The **Deferred / out of scope** section captures things deliberately left out of v0.3.0, not things forgotten.

When in doubt about how strongly to weigh a piece of guidance: principles in the **How** are load-bearing and should be challenged before being discarded. T2 workstream descriptions are first-pass and expected to evolve as their own plans are written. Trade-offs document the decision and its cost; reopening a trade-off means re-doing the work, which is fine but not free.
