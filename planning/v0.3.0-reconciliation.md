# v0.3.0 — Reconciliation audit

Two v0.3.0 design documents exist, plus a worked example prototype. They were produced in separate sessions and make **contradictory structural decisions** on at least five points. This audit maps the divergences and records how each was resolved. The result is a third model -- neither document's position wholesale -- that emerged from working through the trade-offs.

**Status:** decisions resolved (9 June 2026). Ready for implementation.

## The five structural divergences

### 1. Is `exfu/` a scope?

| Pre-direction | Today's doc | Example prototype |
|---|---|---|
| **No.** "Not a scope (no `scope.md`). Owned by ExFu by convention; the user doesn't edit it directly." It's a materialised tier with a distinct internal structure. | **Yes.** "`exfu/` and `user/` are ordinary scopes — same internal folder-types, each with `scope.md`." One uniform concept everywhere. | No. No `scope.md` in `exfu/`. |

**Why it matters:** If exfu/ is a scope, it follows the uniform folder-type catalogue (ontology/, context/, docs/, etc.). If it's not, it has its own specialised structure (ontologies/, conventions/, principles/, recommendations/, templates/). This cascades into what "the base" looks like and how agents discover ExFu-shipped material.

### 2. Can scopes nest?

| Pre-direction | Today's doc | Example prototype |
|---|---|---|
| **No.** "Scopes are not nested inside scopes. Grouping folders can nest; scopes are leaves." | **Yes.** "Scopes nest via their own `scopes/` subdirectory." Self-similar recursion. Each scope gathers children in its own `scopes/`. | No. Scopes are leaves. `acme-q3-renewal/` sits under grouping folders `scopes/teams/sales/projects/`. |

**Why it matters:** This affects the parent-chain model, scope.md's parent field, how agents discover scopes (recursive `scope.md` search vs walk-up), and whether the tree is self-similar or has a structural distinction between "grouping" and "scope" at every level.

### 3. Convention snapshots vs thin pointers

| Pre-direction | Today's doc | Example prototype |
|---|---|---|
| **Snapshots.** "Convention by copy, plugin as source." `agent.md` is copied from `exfu/conventions/<type>/agent.md` into each folder at creation time. The folder is sovereign; upstream changes don't propagate. Explicit principle: "Updates to the upstream template do not automatically rewrite past folders." | **Thin pointers.** `agent.md` is a "thin pointer with mandatory explicit upward references." Behaviour defined once in `exfu/ontology/`; each folder just references it and records local deviations. | Snapshots. Each `agent.md` is a full, self-contained document (~50-60 lines) with complete instructions, not a pointer. |

**Why it matters:** Fundamentally different philosophies. Snapshots = substrate is self-contained, survives plugin removal, folders evolve independently, but drift is possible and the substrate is verbose. Thin pointers = lean, no drift, single source of truth, but the substrate depends on `exfu/` being present, and a shared/extracted scope loses its conventions.

### 4. `exfu/` internal structure

| Pre-direction | Today's doc |
|---|---|
| Seven specialised folders: `ontologies/`, `conventions/`, `principles/`, `recommendations/`, `librarians/`, `skills/`, `templates/`. Each serves a distinct purpose in the ExFu tier. | Same nine folder-types as any scope: `ontology/`, `context/`, `docs/`, `skills/`, `librarians/`, `todo/`, `reminders/`, `inbox/`, `databases/`. (Uniform.) |

**Why it matters:** The pre-direction model gives exfu/ a richer, purpose-built structure (principles, recommendations, conventions as separate first-class concerns). The today model treats exfu/ as just another scope, which is simpler but loses the dedicated homes for conventions, principles, and recommendations.

### 5. Ontology precedence

| Pre-direction | Today's doc |
|---|---|
| **Local-first cascade.** "Precedence is local-first: scope wins over user, user wins over ExFu. Resolution is the agent's job." | **No precedence.** "There is no override mechanism, no reserved words, no cascade-wins rule." Agent reads all, holds multiple meanings, asks user when ambiguous. |

**Why it matters:** Less structural, more philosophical. The pre-direction model gives agents a deterministic resolution rule. Today's model trusts the agent to hold ambiguity. Both are defensible; the question is whether agents reliably handle "hold both meanings" in practice.

## Significant content in pre-direction that today's doc doesn't cover

These aren't contradictions — they're things the pre-direction addresses that today's doc is silent on:

1. **Outcome-framed elicitation.** Each user-facing ontology type ships with an elicitation prompt in user vocabulary. The install agent says "do you want me to capture todos and tasks?" not "do you need a todos folder?" Today's doc doesn't address install UX at this level.

2. **Portable skill definitions (T2-E).** Skills become provider-agnostic definitions rendered into Claude/Gemini/etc at use time. Today's doc doesn't mention this.

3. **User-facing vs infrastructure type split.** The pre-direction explicitly categorises which folder-types are offered during install (todos, contacts, context) vs materialised silently (librarians, conventions, ontologies). Today's doc doesn't distinguish.

4. **Principles as shipped material.** `exfu/principles/` carries reasoning patterns (Golden Circle, outcome-framed elicitation, concrete-first) as discoverable atoms agents read at runtime. Today's doc has no equivalent.

5. **Recommendations catalogue.** `exfu/recommendations/` holds curated third-party suggestions the install agent surfaces in context. Today's doc has no equivalent.

6. **Convention refresh mechanism.** How an existing substrate adopts new ExFu conventions after a plugin update. Today's doc doesn't address this.

7. **Rich `scope.md`.** The pre-direction's scope.md (as shown in the example) has YAML frontmatter (scope, type, parent-grouping, team, created, status, target-close) and structured sections (entities, conventions, current state, dependencies, related skills). Today's doc's scope.md is minimal (name, purpose, parent).

8. **13 open architectural questions.** Many are substantive (migration agent contract, reserved names, schema format, convention refresh, principles/brand-voice/wow boundary). Today's doc has 5 open questions, some overlapping.

## Assessment

The two documents share the same *vision* (uniform scopes, exfu/user/scopes top-level, folder-type catalogue, librarians, collapsing orgs/teams into scopes). But they make different *decisions* at the structural level on five points that cascade into everything else.

The pre-direction is:
- **More detailed** — 13 open questions, five T2 workstreams, install UX principles, portable skills, rich scope.md.
- **More conservative** — convention snapshots (self-contained), scopes as leaves (simpler), exfu/ as a special tier (purpose-built).
- **Backed by a prototype** — the example directory proves the model works in practice.

Today's doc is:
- **More uniform** — one concept everywhere, self-similar recursion, exfu/ as a scope.
- **Simpler in some ways** — thin pointers, minimal scope.md, nine-folder catalogue vs seven specialised exfu/ folders.
- **Bolder on PII** — drops the two-layer boundary entirely.
- **Introduces the visualisation** — HTML substrate map, a genuine addition.

Neither is wrong. They're different sets of trade-offs applied to the same problem.

## Resolved decisions

All five divergences were resolved in conversation on 9 June 2026. The result is neither document's position wholesale -- it's a third model that emerged from working through the trade-offs.

### 1. `exfu/` is a special location, internally structured like a scope

Neither "it's a scope" nor "it's a special tier." exfu/ is a special location in the substrate root (no `scope.md`, not user-editable, owned by the plugin). But internally it uses the same folder-type catalogue as any scope (ontology/, context/, docs/, skills/, librarians/, visualisations/, etc.). Agents discover its contents the same way they discover any scope's contents.

### 2. Scopes nest via `scopes/` subdirectory

Self-similar recursion. A scope gathers child scopes in its own `scopes/` directory. Each nested scope explicitly declares its parent so that if the scope is shared or extracted, the agent knows something is missing from its ontologies.

### 3. Reference + delta (package management model)

Neither convention snapshots nor thin pointers. The model draws from modern package management (npm lockfiles, Kustomize overlays, Dependabot drift detection):

- **agent.md references** the upstream convention: "This folder follows exfu/v0.3/ontology/todos/"
- **agent.md records only local deviations**: "In this scope, todos also track client-facing deadlines"
- **agent.md does NOT copy** the upstream convention content
- The upstream convention in `exfu/<version>/` is the single source of truth
- A librarian can detect when the upstream changed and flag it for the user/agent
- No automatic propagation -- the user decides when to update (like merging a Dependabot PR)

**Protective header.** Both scope.md and agent.md open with a guard: "This folder follows ExFu conventions. If you haven't loaded them yet, ask your user to set you up with their WoW or ExFu skills." This catches agents that wander into the substrate without context.

### 4. Minimal `scope.md` with protective header

scope.md carries: name, purpose, parent declaration, and the protective header. That's it. No duplicated entities, conventions, current state, or dependencies -- those live in their respective folder-types and are the source of truth.

The rich cross-referencing view lives in the **single global index** (see versioning model below), maintained by librarians. No per-scope index.md. The central index gives agents a true picture of the whole substrate, which is far more useful for the cross-referencing chaos of real-world projects than isolated per-scope snapshots.

### 5. Ontology: accept the chaos, discipline at write-time

No automatic cascade. No deterministic precedence rule. Ontology conflicts in a real human workspace can be orthogonal (two unrelated meanings), overrides (scope intentionally redefines a term), or extensions (scope adds nuance to a broader definition). A cascade rule can't distinguish these.

Instead:

- **Reading agents** are aware that conflicts may exist. They read all relevant ontologies and use judgement. When a conflict is genuinely ambiguous, they ask the user.
- **Writing agents** must annotate intent when creating ontologies that touch existing terms. "This extends the user-level definition of 'qualified lead' with sales-specific criteria" or "This scope uses 'sprint' differently from the engineering team scope." The annotation is for later consuming agents.
- Ontologies may be **lifted** (a scope definition gets promoted to user-level) or **independently conflict** (two scopes define the same term without knowing about each other). Perfect world state is not achievable. Best efforts.

### 6. Versioned `exfu/` with side-by-side installation

A new structural decision that emerged from the convention management discussion. exfu/ is versioned using semver breaking-change boundaries:

```
substrate/
  exfu/
    v0.3/                    # pre-1.0: minor = breaking
      ontology/
      skills/
      librarians/
      ...
    v0.6/                    # new breaking version
      ...
    v1/                      # post-1.0: major only
      ...
    latest -> v0.6/          # symlink, new scopes default here
    derived/                 # unversioned, generated content
      index.json             # single global index
      ...                    # visualisation, computed state
  user/
    scope.md                 # no version pin
    ...
  scopes/
    some-scope/
      scope.md               # declares: expects exfu v0.3
```

**Version directory naming.** Pre-1.0, the directory is the minor version (v0.3, v0.6) because in semver, pre-1.0 minors CAN be breaking. Post-1.0, the directory is the major version (v1, v3) because only majors break. Patches and non-breaking minors update in-place within the existing version directory.

**Scope pinning.** scope.md declares which exfu version the scope expects. agent.md references the versioned path (exfu/v0.3/ontology/todos/). New scopes default to `latest`.

**Side-by-side installation.** Plugin updates install the new version directory alongside existing ones and flip the `latest` symlink. Existing scopes keep working against their pinned version. Agents entering a scope see the pin, can surface "v0.6 is available, here's what changed" when appropriate.

**Migration instructions live in the plugin, not the substrate.** The plugin ships migration docs that agents read at runtime. The substrate stays clean -- no migration artifacts cluttering the user's files.

**User scope is unversioned.** `user/` does not pin a version. Migration is applied by user decision, with the agent offering guidance based on the plugin's migration instructions. Users can be told how to continue using an older version if they prefer.

**Single global index.** One index in `exfu/derived/`, with sections for each version in use. Each version's indexing librarian contributes to the global index. This gives agents a true whole-substrate picture and lets version-specific librarians continue working independently.

**Librarian cleanup.** A librarian periodically checks whether old version directories are still referenced by any scope. Unreferenced versions are flagged for deletion.

**Other librarians.** Whether a given librarian is version-specific or global will be solved case-by-case as librarians are built. The nightly index librarian is clearly global; convention-aware librarians may be version-specific. Not over-engineering this now.
