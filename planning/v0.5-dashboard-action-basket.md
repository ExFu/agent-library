# v0.5 -- the dashboard Action Basket and the read-side quick wins

Design + implementation record for the 0.5.0 release, validated with Al 2026-07-22.
This document is the anchor for the round: why the dashboard gained an interaction
model without gaining actuators, exactly what shipped, and what stayed out of scope.

---

## Why

The dashboard was deliberately read-only. Everywhere a user might want to act it
printed guidance ("to create a scope, tell your AI ..."), which teaches the
conversational model but makes looking at the dashboard create chores: every
glance ends with a trip to a chat window to type out what the page already knows.

The actuator problem is what kept it read-only. T3-dashboard-actions researched
the trigger mechanisms (deep links, routines, action servers, request queues) and
none of the instant ones are free of infrastructure. Al's insight, 2026-07-22:
skip actuators entirely. Let every interaction accrete an instruction into an
editable list, and let the user hand that list to their AI in one go. Visual
"changes" with zero programmatic writes, and the prompt the user watches being
built is itself a lesson in how to talk to the library.

Provenance: the 2026-07-20 dashboard-improvement-shortlist inbox item, plus Al's
accreting-prompt steer. The deep-link half rests on T3-dashboard-actions'
verified research (claude://cowork/new?q=, ~14k char prefill, interactive
allowance, user confirms by sending).

## How

**The Action Basket.** All client-side, inside the generated page; works from
file:// with no server. State lives in localStorage keyed by library root.
Interaction points queue instructions: task checkboxes (tick/untick), bin
affordances (mark for deletion), + New task / scope / reminder / capture forms,
ask-about inputs in the sidebar, and suggest buttons on guidance lines (queue
install for a staged agent, queue an investigation for a failing one, queue a
refresh from the staleness banner). Each instruction embeds the concrete
relative path the page already knows. The drawer supports inline edit, reorder,
remove, and free-text additions. Export is Copy prompt (preamble with snapshot
timestamp, numbered instructions, closing index-refresh line) or Open in Claude
(the deep link; disabled past ~13k encoded chars in favour of Copy). Queued
changes render optimistically (dashed amber, "queued" chip) via overlay keys
(kind : rel+file : title); clicking the same control again unqueues it; items
from an older page snapshot are flagged and their overlays only apply while the
key still matches. Nothing on disk changes until the user's AI does the work.

**Read-side quick wins, same round:**

- Pointer chips ("Managed in ClickUp") link out when the folder's own agent.md
  names a URL; never fabricated (T3-dashboard-workspace-views rule).
- Reminders group Overdue / Coming up (7 days) / the rest, best-effort from the
  first ISO date; undated entries render as before. Bullet titles shed checkbox
  markers and leading dates.
- "How it works" tab renders the core ontology.md: folder-type catalogue as a
  card grid, full conventions as collapsibles. Sidebar additionally surfaces
  each scope's ontology/ files beside context/.
- Staleness banner past 36 hours, with a queue-a-refresh action.
- Gallery at the foot of Your scopes: every visualisations/ bundle across
  scopes, manifest or not; view:true bundles still mount as tabs.

## What shipped

- `plugin/src/shared/scheduled-tasks/scheduled-agents/dashboard-generator.py`:
  basket JS + CSS, interaction wiring, ontology renderer, gallery collector,
  date classification, pointer URL extraction; stray duplicate
  grouping_label/hint definitions removed.
- Example library enriched to demo the new surfaces (dated reminders.md, inbox
  capture with triage status, ClickUp board URL); dashboard regenerated; the
  example's stale pre-gallery dashboard-generator librarian def synced.
- Manifests to 0.5.0 (features = minor per the changelog's own rule),
  CHANGELOG entry, librarian def updated to describe the new views.

Verified end-to-end in the browser (tick, delete, create, reorder, edit,
unqueue, copy-prompt assembly, deep link, reload persistence, stale-overlay
behaviour) plus generator compile/dup-def checks and payload inspection.

## Deliberately not in this round

Action server, routine /fire wiring, the app/data bundle split, MCP Apps,
client-side search, per-scope freshness heat, Dropbox conflicted-copy alerts.
The basket needs none of them; the remaining shortlist proposals stand. Dist
zips are a separate release step (build.sh all --dist).
