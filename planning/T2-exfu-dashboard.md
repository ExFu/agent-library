# T2 -- ExFu dashboard

A unified visual interface for substrate state, librarian health, and daily workspace views. One HTML application, multiple views, no external dependencies.

---

## Why

The substrate is invisible. It's files in folders, read by agents that load skills. A user has no way to see what they've built, whether it's healthy, or what's happening in it, without asking Claude to go look. That's fine for power users in conversation, but it fails in two cases:

1. **Orientation.** A returning user wants a quick picture: what scopes do I have, what's populated, what's stale? Reading scope.md files one at a time is slow and fragmented.
2. **Confidence.** Librarians run overnight. Did they work? Is the index fresh? Are any failing? Without a visual signal, the user has to trust that everything worked, and trust doesn't scale.

The dashboard makes the substrate tangible. It renders the same data agents use (the index, the librarian registry, the run log) into something a human can scan in seconds.

## How

### Architecture

A static app bundle (HTML with embedded CSS and JavaScript -- no build step, no framework, no external dependencies) plus a generated data file alongside it. Lives in the substrate's visualisations gallery and opens in any browser straight from disk.

Data sources:
- `exfu/derived/index.json` -- substrate state (scope tree, folder-types, version pins)
- `exfu/derived/agent-registry.json` -- registered scheduled agents (librarians + business agents), status
- `exfu/derived/agent-log.json` -- run history
- Individual scope folder data (todo, reminders, inbox files read at generation time)
- Normalised workspace feeds from scopes that deviate from the sane defaults (see the adaptor strategy in `T3-dashboard-workspace-views.md`)

The dashboard is regenerated by a librarian (or on demand) whenever the underlying data changes. It reads JSON and renders client-side; no server needed.

### The view registry (added 10 June 2026)

Tabs are not hand-wired; they come from a registry the generator assembles. Built-in views first (Your scopes, Agents, then one view per workspace ontology -- Todos, Reminders, Inbox -- all rendered from the same per-folder-type template with their own creation guidance), then **scope-provided views**: any scope's `visualisations/<name>/` bundle with a `viz.md` manifest declaring `view: true` mounts automatically as a top-level tab, embedded by relative iframe. This is the pluggable half of the gallery idea: a scope can define a visualisation for one of its ontologies and the dashboard picks it up with no central changes. Manifest fields: `name`, `view`, optional `entry` (default index.html) and `description`. The example substrate's side-project scope demonstrates it ("Trend snapshot").

### Views

**1. Substrate map**

Not a filesystem tree. A conceptual view showing:
- Scopes as cards or nodes, arranged by relationship (parent/child via nesting, not indented file paths)
- Each scope shows: name, purpose, which folder-types are populated (as small icons or badges), version pin
- Visual distinction between data-bearing, pointer, and empty folder-types
- The user/ scope highlighted as the personal layer
- exfu/ shown as the convention source, not as a peer scope

The map answers: "what do I have, and where is it?"

**2. Librarian dashboard**

- Registered scheduled agents -- both kinds, librarians (substrate remit) and business agents (domain remit) -- as a list or grid, grouped by kind within cadence
- Each shows: name, cadence, last run time, status (healthy/warning/failing)
- Run history as a timeline or recent-runs table
- Unregistered definitions flagged (found but not installed)
- Disabled librarians shown but dimmed

The dashboard answers: "is my substrate healthy?"

**3. Workspace views**

For folder-types with sane defaults (todo, reminders, inbox), render the actual content:

- **Todo view:** tasks from data-bearing or pointer todo/ folders across scopes. For pointers, show the pointer target. For data, render the tasks.
- **Reminders view:** upcoming and overdue reminders across scopes.
- **Inbox view:** unsorted items across scopes, with triage status if the inbox librarian has run.

These views are optional; they only appear if the user has content in these folder-types. They answer: "what's on my plate?"

Workspace rendering follows an adaptor strategy: a normalised data shape, shipped parsers for the sane-default formats, and the option for a deviating scope to provide its own normalised feed. Detail in `T3-dashboard-workspace-views.md`.

**4. Visualisations gallery (added 10 June 2026)**

Visualisations are not only ExFu-shipped: any scope's `visualisations/` folder can carry its own bundles (a client report, a database chart, a trip map). The dashboard should surface them -- a gallery section listing every visualisation the index discovers across scopes, with name, owning scope, and a link to open it. Convention sketch: each visualisation subfolder carries a small manifest (name, one-line description, entry file); the nightly index records them; the gallery renders the list. Plug-and-play: drop a bundle in a scope's visualisations/ folder and it appears on the dashboard after the next index run. This stays deliberately thin until a second real visualisation exists to design against.

### Actions (added 10 June 2026)

The dashboard grows buttons for maintenance: re-run the index, regenerate the dashboard, re-run a failing scheduled agent. Two classes of action, very different costs:

- **Deterministic actions** are scripts (the index, the dashboard generator). No agent needed; anything that can execute a local script can serve them.
- **Agent actions** (inbox triage, a full cadence run) need a Claude session, and must run on the user's existing subscription allowance -- never metered API billing, never an embedded API key.

How a click in a static local page reaches either class is the open hurdle, and it gets its own plan: `T3-dashboard-actions.md`. Content management (creating tasks, dismissing reminders) stays out of scope; actions are about maintaining the substrate, not managing its contents.

### Visual language

- Warm earth-tone palette (consistent with the ExFu website)
- Cards and badges over tables and trees
- Scannable at a glance; details on click/hover
- No technical jargon in labels ("Your scopes" not "Scope tree", "Maintenance" not "Librarian registry")
- Guidance where buttons aren't: short "to do X, tell Claude ..." lines in context, plus small ? hints that explain concepts (what a scope is, what an agent is) right where they appear
- Major views offer two presentations behind a List/Map toggle: a scannable card list, and a radial map (the user at the centre) with type filters and a click-to-open node sidebar

### Generation approach (resolved 10 June 2026)

The original options were full static generation (A: data embedded in one self-contained file) versus client-side loading of JSON (B: always current, but blocked by `file://` CORS). v1 shipped as option A. The bundle split refines it into a hybrid that keeps A's reliability and gains B's cheap refresh:

- The **app** is static and stable -- generated once per dashboard version, not per data change.
- The **data** is a JavaScript file (`dashboard-data.js`) the page loads with a relative `<script src>` tag. Script tags work from `file://`; it's `fetch()` that CORS blocks. Refreshing the dashboard means rewriting one small data file, not reassembling the page.

### Placement

**Decision (10 June 2026, revised in review with Al):** the dashboard lives in the substrate's visualisations gallery at `exfu/visualisations/dashboard/` -- visual outputs are literally what that folder is for. The artefact splits in two:

- **App bundle** -- `index.html` plus any assets. Stable; only changes when the plugin ships a new dashboard version.
- **Data file** -- `dashboard-data.js`, rewritten by the generator on every run. Loaded by the page via a relative `<script src>` tag, which works from `file://` with no server and no CORS trouble.

`exfu/derived/` remains the machine-state *source* (index, registry, log) the data file is built from; the dashboard artefact itself does not live there. The path is deliberately unversioned: a user's bookmark or desktop shortcut survives convention-base upgrades. (An earlier pass that day placed the whole generated file in `exfu/derived/dashboard/` on regenerable-state grounds; review reversed it -- the gallery is the user-facing home, and derived/ shouldn't come into it.) Full reasoning: `T3-dashboard-generation.md`, decision 1.

### Trade-offs

- **One file vs multi-file.** Resolved by the bundle split: a stable app file plus a separate data file. The app itself stays a single HTML file for simplicity; the data lives apart so a refresh rewrites kilobytes, not the app.
- **Static vs dynamic.** Resolved as the hybrid above: static app, regenerated data file, loaded via `<script src>` so `file://` works. Portability of static, refresh cost of dynamic.
- **Scope of workspace views.** Full task management in the dashboard would duplicate external tools (ClickUp, Linear). The workspace views are read-only summaries, not management interfaces. "Here's what's on your plate" not "manage your tasks here."

### Open questions

1. **Trigger mechanism for agent actions.** How a button in a local page causes agent work, on subscription allowance. Candidates and research live in `T3-dashboard-actions.md`.
2. **Gallery manifest.** What a scope visualisation declares about itself (name, description, entry file) and where (frontmatter file in its subfolder, most likely). Decide when the gallery view gets built.
3. **Sane-default format grammar.** The default templates landed in the M2 conventions revision (`templates/defaults/`); what remains is pinning the task-line and reminder-date grammar the workspace parsers rely on (see `T3-dashboard-workspace-views.md`).
4. **Mobile/responsive.** The dashboard should work on mobile (users may scan it on their phone). Responsive layout from the start.

Settled this round: pointer rendering (chip + source line -- `T3-dashboard-workspace-views.md`), multi-substrate (each substrate its own dashboard, no aggregation), refresh verb (the substrate skill points at the generator script -- `T3-dashboard-generation.md`).
