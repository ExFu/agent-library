# T2 -- ExFu dashboard

A unified visual interface for substrate state, librarian health, and daily workspace views. One HTML application, multiple views, no external dependencies.

---

## Why

The substrate is invisible. It's files in folders, read by agents that load skills. A user has no way to see what they've built, whether it's healthy, or what's happening in it, without asking Claude to go look. That's fine for power users in conversation, but it fails in two cases:

1. **Orientation.** A returning user wants a quick picture: what scopes do I have, what's populated, what's stale? Reading scope.md files one at a time is slow and fragmented.
2. **Confidence.** Librarians run overnight. Did they work? Is the index fresh? Are any failing? Without a visual signal, the user has to trust that everything worked, and trust doesn't scale.

The dashboard makes the substrate tangible. It renders the same data agents use (the index, the librarian registry, the run log) into something a human can scan in seconds.

## How

### Architecture

A standalone HTML file with embedded CSS and JavaScript. No build step, no framework, no external dependencies. Lives in the substrate's visualisations folder and opens in any browser.

Data sources:
- `exfu/derived/index.json` -- substrate state (scope tree, folder-types, version pins)
- `exfu/derived/librarian-registry.json` -- registered librarians, status
- `exfu/derived/librarian-log.json` -- run history
- Individual scope folder data (todo, reminders, inbox files read at generation time)

The dashboard is regenerated by a librarian (or on demand) whenever the underlying data changes. It reads JSON and renders client-side; no server needed.

### Views

**1. Substrate map**

Not a filesystem tree. A conceptual view showing:
- Scopes as cards or nodes, arranged by relationship (parent/child via nesting, not indented file paths)
- Each scope shows: name, purpose, which folder-types are populated (as small icons or badges), version pin
- Visual distinction between data-bearing, pointer, and empty folder-types
- The user/ scope highlighted as the personal layer
- exfu/ shown as the convention source, not as a peer scope

The map answers: "what do I have, and where is it?"

**2. Librarian dashboard**

- Registered librarians as a list or grid
- Each shows: name, cadence, last run time, status (healthy/warning/failing)
- Run history as a timeline or recent-runs table
- Unregistered definitions flagged (found but not installed)
- Disabled librarians shown but dimmed

The dashboard answers: "is my substrate healthy?"

**3. Workspace views**

For folder-types with sane defaults (todo, reminders, inbox), render the actual content:

- **Todo view:** tasks from data-bearing or pointer todo/ folders across scopes. For pointers, show the pointer target. For data, render the tasks.
- **Reminders view:** upcoming and overdue reminders across scopes.
- **Inbox view:** unsorted items across scopes, with triage status if the inbox librarian has run.

These views are optional; they only appear if the user has content in these folder-types. They answer: "what's on my plate?"

### Visual language

- Warm earth-tone palette (consistent with the ExFu website)
- Cards and badges over tables and trees
- Scannable at a glance; details on click/hover
- No technical jargon in labels ("Your scopes" not "Scope tree", "Maintenance" not "Librarian registry")

### Generation approaches

Two options (decide during implementation):

**A. Static generation.** A Python script (or librarian) reads the data sources and generates a self-contained HTML file with the data embedded as JSON. The file opens offline. Regenerated nightly or on demand.

**B. Client-side loading.** A static HTML file that uses JavaScript to read the JSON files from relative paths. Works when opened from the substrate directory. No generation step needed, but requires the browser to allow local file access (or a simple local server).

Option A is more reliable (no CORS issues, works anywhere). Option B is simpler to maintain. Probably A for the initial version.

### Placement

The generated dashboard lives at:
```
exfu/v0.3/visualisations/substrate-dashboard/
  index.html          # the dashboard
  dashboard-data.json # embedded or alongside (depending on approach)
```

A shortcut or alias at the substrate root could make it easier to find.

These T3s can be written when M2.1 implementation begins. The T2 provides the architectural direction.

### Trade-offs

- **One file vs multi-file.** A single HTML file is simpler to distribute and open. Multiple files (HTML + CSS + JS) are easier to maintain. We pick single file for v1; it's small enough.
- **Static vs dynamic.** Static generation (option A) is more portable but stale between runs. Dynamic loading (option B) is always current but has environment constraints. We pick static for reliability.
- **Scope of workspace views.** Full task management in the dashboard would duplicate external tools (ClickUp, Linear). The workspace views are read-only summaries, not management interfaces. "Here's what's on your plate" not "manage your tasks here."

### Open questions

1. **Pointer rendering.** For folder-types that point to external tools, should the dashboard show a link to the tool, a last-synced timestamp, or just "managed in ClickUp"?
2. **Multi-substrate.** If a user has multiple substrates, each gets its own dashboard. No aggregation for now.
3. **Mobile/responsive.** The dashboard should work on mobile (users may scan it on their phone). Responsive layout from the start.
4. **Refresh trigger.** Besides nightly generation, should the substrate skill offer a "refresh dashboard" verb?
