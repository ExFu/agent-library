# T3 -- Versioning infrastructure

Implement the versioned exfu/ directory structure, the `latest` symlink (with fallback), the derived/ directory for generated content, and version pinning in scope.md.

**Parents:** `T2-substrate-architecture.md` (domain), `M2-substrate-redesign.md` (milestone)
**Prerequisites:** T3-convention-base (the v0.3/ directory must exist as the first version)
**Status:** not started.

---

## Why

The versioning model is what makes convention updates safe. Without it, a plugin update that changes conventions silently breaks every scope in the substrate. With it, existing scopes keep working against their pinned version, new versions install alongside, and migration is an explicit user decision.

This also establishes the derived/ directory -- the home for the global index and other generated content that doesn't belong inside a version.

---

## What to build

### 1. Version directory structure

The convention base (T3-convention-base) creates `exfu/v0.3/`. This T3 wraps it in the versioning infrastructure:

```
exfu/
  v0.3/                    # convention set (built by T3-convention-base)
    ontology/
    ...
  latest -> v0.3/          # symlink to current version
  derived/                 # unversioned generated content
    index.json             # placeholder (populated by T3-nightly-index)
```

### 2. The `latest` symlink

**Primary mechanism:** A filesystem symlink at `exfu/latest` pointing to the current version directory.

```bash
ln -s v0.3 exfu/latest
```

New scopes default to `latest` -- their scope.md says `exfu: latest` (resolved to the actual version at creation time) or the agent reads through the symlink.

**Fallback for environments without symlink support:**

Box (used by solo plugin) may not support symlinks. Windows without developer mode doesn't support them. For these environments, a fallback file:

```
exfu/latest.txt
```

Contents: a single line with the version directory name.

```
v0.3
```

The substrate skill checks for the symlink first, falls back to latest.txt. The install skill creates whichever the environment supports.

### 3. derived/ directory

Home for generated, unversioned content:

```
exfu/derived/
  index.json              # global substrate index (T3-nightly-index)
```

Rules:
- Nothing in derived/ is hand-edited. Everything is generated by librarians or tools.
- derived/ is not a folder-type (no agent.md). It's infrastructure.
- The nightly index librarian owns index.json. Other librarians or tools may add files here in future.
- derived/ is safe to delete and regenerate. It's a cache, not a source of truth.

### 4. Version pinning in scope.md

scope.md's YAML frontmatter includes:

```yaml
exfu: v0.3
```

This tells agents which convention base to read for this scope. The agent resolves references like `exfu/v0.3/ontology/folder-types/todo.md` using this pin.

**Pinning rules:**
- New scopes: pinned to whatever `latest` resolves to at creation time
- Existing scopes: keep their pin across plugin updates
- user/ scope: no pin (unversioned). Always reads through `latest`.
- Migration: an agent updates the pin after applying migration steps

### 5. Side-by-side installation

When a plugin update ships a new breaking version (e.g. v0.6), the install/update process:

1. Creates `exfu/v0.6/` alongside `exfu/v0.3/`
2. Updates the `latest` symlink (or latest.txt) to point to v0.6
3. Does NOT touch existing scopes' pins
4. Does NOT delete v0.3/
5. Surfaces to the user: "v0.6 is now available. Your scopes still use v0.3. Would you like to migrate any?"

Migration instructions live in the plugin (not the substrate). The agent reads them at runtime when the user asks to migrate.

### 6. Librarian cleanup

A librarian (defined in the convention base, implemented whenever librarians are built) periodically:

1. Reads the global index to find all exfu version pins in use
2. Compares against version directories that exist in exfu/
3. Flags any version directory not referenced by any scope and not pointed to by `latest`
4. Offers to delete unreferenced versions (with user confirmation)

For M2, this is a *definition* (documented in the convention base), not a running librarian. Librarian implementation is M3.

## Implementation notes

### Build system integration

The build system (T3-build-system) needs to know about versioning:

- The plugin source contains `substrate/exfu/v0.3/` (the convention base)
- At install time, this is copied into the user's substrate
- The install skill creates the `latest` symlink/file and `derived/` directory
- Future plugin versions may ship a new version directory to install alongside

### Testing the symlink fallback

During implementation, test:
1. macOS/Linux: symlink works natively
2. Windows with developer mode: symlink works
3. Windows without developer mode: latest.txt fallback
4. Box filesystem: test whether symlinks survive Box sync. If not, use latest.txt for all Box users.

## Acceptance criteria

1. `exfu/latest` symlink exists and resolves correctly
2. `exfu/latest.txt` fallback exists with the version name
3. `exfu/derived/` directory exists with placeholder index.json
4. scope.md template includes the `exfu:` version pin field
5. user/ scope.md template omits the version pin
6. The substrate skill (or documentation) describes how to resolve version pins
7. Side-by-side installation process is documented
8. Cleanup librarian is defined (not implemented) in the convention base
