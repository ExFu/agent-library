# v0.3.0 — Substrate revision: the scope-based substrate

Planning doc for the v0.3.0 plugin release. A fundamental redesign of the substrate's folder model around a single, uniform, recursive concept: the **scope**.

This document is a design doc. It captures the reasoning and the target shape. Implementation is a separate step. Anchors back to: `T1-overview.md`, `v0.2.0-substrate-revision.md`, `cross-cut-storage-architecture.md`.

**Status:** design validated, not yet implemented.

---

## Why

The v0.2.0 substrate works, but its structural model carries tensions that compound as usage grows:

1. **Multiple structural concepts for the same thing.** v0.2.0 has `orgs/`, `teams/`, `scopes/`, and a personal default layer — each with slightly different conventions, different hard/soft folder rules, and different metadata schemas. But conceptually they're all the same thing: a bounded context with its own knowledge, definitions, and conventions. An org is a scope. A team is a scope. A personal space is a scope. Making them structurally different creates complexity that doesn't earn its keep.

2. **Agent discovery is ad hoc.** An agent landing in a v0.2.0 substrate has to know the structural differences between `orgs/`, `teams/`, `scopes/`, and the personal top-level, then navigate each differently. There's no uniform "enter any scope, find the same shape" convention. Discovery depends on the substrate skill knowing the layout rather than the layout being self-describing.

3. **No standard vocabulary for common folder types.** Most knowledge-work scopes need the same kinds of things: tasks, reminders, reference material, definitions, captured documents, structured records. v0.2.0 has `context/` and `databases/` but leaves the rest to convention drift. Every install invents its own answer to "where do reminders go?" and "where do I put a definition of what this team calls things?"

4. **The PII two-layer model is too rigid.** v0.2.0 hard-bans PII from the substrate and requires a separate access-controlled Layer 2 store. In practice, the substrate *is* where people need to store contacts, org charts, CRM records, and working notes about real humans. The two-layer model forces operational complexity (a database, a connector, access-control plumbing) onto every user who just wants to remember someone's name.

5. **No standard place for maintenance agent definitions.** v0.2.0 has scheduled tasks but no convention for where to define them per-scope, or how an agent discovers what maintenance is supposed to happen.

6. **No way to see the substrate without opening folders.** Users have to browse the filesystem manually to understand what's in their substrate. There's no visual overview.

This revision replaces the multi-concept structural model with one uniform concept (the scope), defines a standard folder-type vocabulary (so agents always know where to look), simplifies data rules (secrets-only ban, no PII machinery), and adds a substrate visualisation as a first-class deliverable.

## How

### Principles

- **One concept: the scope.** Everything is a scope. An org is a scope. A team is a scope. A personal space is a scope. A project is a scope. The ExFu plugin's own content is a scope. Every scope has the same internal shape, the same conventions, the same discovery model. The structural differences between `orgs/`, `teams/`, `scopes/`, and the personal layer collapse into one uniform thing.
- **Self-similar recursion.** A scope can contain child scopes, gathered in its own `scopes/` directory. The pattern repeats at every level. An agent entering any scope at any depth sees a predictable shape.
- **Folder types are a discovery convention, not a storage mandate.** Each standard folder type (ontology, context, docs, skills, etc.) answers "how does this scope handle this kind of thing?" The answer may be "the data lives here" or "the data lives in ClickUp; this folder just says so." The point is that an agent always knows *where to ask*, not that the data is always local.
- **Explicit upward references, never magic.** Every scope declares its parent. Every folder's `agent.md` names the base it builds on. An agent never relies on implicit knowledge or filesystem-position guessing. If a scope is extracted or shared in isolation, the missing parent is immediately visible.
- **Ontologies are reference, not precedence.** An agent reads all relevant ontologies (exfu base, user, each ancestor scope, active scope) and holds them together. There is no override mechanism, no reserved words, no cascade-wins rule. When definitions conflict, the agent recognises both and asks the user in context.
- **Secrets are banned; everything else is data.** Keys, tokens, passwords, and credential files never enter the substrate. Names, contacts, org charts, CRM records, personal notes — that's just data. It lives where it naturally belongs. The v0.2.0 two-layer PII boundary is retired.
- **Trust the agent.** Rich context plus hard constraints, not procedural scripts. This is unchanged from v0.1.0.

### Top-level structure

The substrate root is a single folder, **`claude/` by default** (the user can rename it; the name is a sane default, not load-bearing). Inside it, exactly three things:

```
claude/                         ← substrate root (renameable)
├── exfu/                       ← special scope: plugin-owned definitions, index, defaults
│   ├── scope.md
│   ├── ontology/               ← base vocabulary (what is a scope, a librarian, etc.)
│   ├── context/
│   ├── librarians/             ← exfu-owned maintenance agents (e.g. the nightly index)
│   ├── databases/
│   └── ...                     ← any other folder-types as needed
├── user/                       ← special scope: the user's personal context & ontology
│   ├── scope.md
│   ├── ontology/               ← personal definitions, ways of working
│   ├── context/                ← personal background (Myers-Briggs, preferences, etc.)
│   ├── skills/
│   ├── reminders/
│   ├── inbox/
│   └── ...
└── scopes/                     ← the tree of everything else
    ├── acme/                   ← a scope (has scope.md)
    │   ├── scope.md
    │   ├── ontology/
    │   ├── context/
    │   ├── todo/
    │   ├── databases/
    │   └── scopes/             ← acme's children, quarantined here
    │       ├── sales/          ← sub-scope
    │       │   ├── scope.md
    │       │   ├── ontology/
    │       │   └── scopes/     ← could nest further
    │       └── eng/            ← sub-scope
    ├── clients/                ← a grouping folder (no scope.md, purely organisational)
    │   └── ...
    └── side-project/           ← another scope
        ├── scope.md
        └── ...
```

**`exfu/` and `user/` are ordinary scopes** — same internal folder-types, each with `scope.md`. They are special only in that they sit at fixed, known positions at the root and play privileged roles:

- **`exfu/`** is the canonical source of base definitions: the folder-type catalogue, what a librarian is, the difference between a todo and a reminder, what the inbox is for. It also owns the nightly index and the substrate visualisation data.
- **`user/`** holds context and ontology that travel with the user across every scope — personal definitions, ways of working, preferences.

**`scopes/`** is an arbitrary-depth tree. A folder inside it is one of two kinds:
- **Grouping folder** — no `scope.md`. Purely organisational (e.g. `scopes/clients/`). An agent ignores it structurally.
- **Scope** — has `scope.md`. A real working context.

**Scopes nest via their own `scopes/` directory.** A scope never holds child scopes loose among its own working folders. It gathers them in a dedicated `scopes/` subdirectory, keeping the scope's own folder-types clean and predictable. The pattern is self-similar: the root has `scopes/`, a scope can have `scopes/`, and so on.

### `scope.md`

The scope marker. Its presence is what distinguishes a scope from a grouping folder. Keep it simple — it's there for a librarian to find and index. The librarian will generate projections of what actually exists.

Contents:
- **Name** — the scope's human-readable name.
- **Purpose** — a one-line description.
- **Parent** — an explicit declaration of this scope's parent scope (path or name). Mandatory for any scope under `scopes/`. This is a portability safeguard: if someone shares or extracts a nested scope on its own, the agent immediately knows something is missing (the parent's ontologies and context aren't present) rather than silently operating with an incomplete picture.

`exfu/` and `user/` have no parent declaration (they are root-level special scopes).

### The folder-type catalogue

Inside any scope, the folder-types are the standard vocabulary of "where things go." Each is a discovery convention first, a storage location second. Its job is to tell an agent *how the user handles this kind of thing for this scope* — whether the data lives here, or somewhere else entirely.

The base catalogue (defined canonically in `exfu/ontology/`):

| Folder | What it answers | Analogy |
|---|---|---|
| `ontology/` | What do the concepts and terms in this scope mean? | A glossary |
| `context/` | What background should an agent know about this scope? | A wiki |
| `docs/` | Where are captured documents that need keeping? | A drawer |
| `skills/` | What skill definitions or drafts relate to this scope? | Functions |
| `librarians/` | What scheduled maintenance should happen here? | Cron jobs |
| `todo/` | How does this scope handle tasks? | A task type |
| `reminders/` | How does this scope handle lightweight nudges? | A data type |
| `inbox/` | Where do uncategorised thoughts go for this scope? | A catch-all |
| `databases/` | Where is structured data with schemas for this scope? | Structured records |
| `visualisations/` | Where do agent-created visual outputs live for this scope? | A gallery |

**The catalogue is open.** Any scope may add a folder-type not listed here. If it does, it should define the new type in that scope's `ontology/` so an agent can make sense of it.

**Store-or-point is a first-class choice for every folder-type.** A `todo/` folder may contain actual task files, or its `agent.md` may simply say "tasks are in ClickUp." A `reminders/` folder may hold a markdown file with natural-language trigger rules, or it may say "reminders live in Apple Reminders." The convention guarantees the *location is discoverable*; whether data lives there is per-scope, per-user.

### The `agent.md` / `readme.md` convention

Every folder-type directory contains two files:

- **`agent.md`** — for agents. Thin, but with mandatory explicit upward references. It opens by naming the definitions it builds on, then lists only this folder's local deviations. Example:

  ```markdown
  Builds on sane defaults from the ExFu plugin (cf exfu/ special scope).
  Familiarise yourself with that deeply before continuing to ensure full
  comprehension.

  Custom instructions:
  - Todos live in ClickUp. This folder does not store tasks directly.
  - Use the ClickUp MCP connector to read/write tasks for this scope.
  - Tag all tasks with the scope name "acme-sales".
  ```

- **`readme.md`** — the same information, for human eyes.

A standard folder with no deviations is therefore tiny: a reference to the base definitions and nothing else. The canonical behaviour of each folder-type lives once, in `exfu/ontology/`. This keeps the substrate lean and prevents convention drift across copies.

### Ontology & concept resolution

**What an ontology folder is.** A collection of definitions — "here is what this concept means in this scope." Each definition is a file (or a section in a file, depending on density).

- `exfu/ontology/` defines the structural vocabulary the entire substrate runs on: what a scope is, what a librarian is, the difference between a todo and a reminder, what the inbox is for, what databases/ contains, what each folder-type means.
- `user/ontology/` adds the user's personal definitions and ways of working that apply across all their scopes.
- Any scope's `ontology/` adds definitions local to that scope ("we call them specialists, not reps"; "a lead in this context means...").

**How resolution works.** When an agent operates inside a scope, it reads all the relevant ontologies by walking the declared parent chain: active scope → each ancestor scope → `user/` → `exfu/` base. It holds them all together. If two levels define a term differently, the agent does not mechanically pick a winner — it recognises both meanings and, where it matters, asks the user in the moment which applies. Sometimes both are in play in a single conversation, and that's fine.

The explicit parent declarations in `scope.md` and the explicit references in `agent.md` are what make this work. They tell the agent *which ontologies are relevant* without filesystem guesswork. The structure makes the reference set discoverable; the agent supplies the judgement.

### Librarians

Librarians are to scheduled tasks what skills are to functions. A librarian is a *definition* of a maintenance agent that runs semi-regularly (typically nightly) to tidy the substrate so the user doesn't have to. The definition lives in a scope's `librarians/` folder. The *actual scheduling* is done by the platform — a Claude Cowork scheduled task, a Gemini equivalent, or whatever the user's AI platform provides. The librarian file is the spec; the platform is the cron.

**What librarians do, by example:**
- Sweep the inbox — take captured thoughts and route them to where they belong (context, a todo, an ontology note, a doc), or leave them if that's the user's preference for this scope.
- Reconcile todos & reminders — clear completed todos; read every in-scope `reminders/` folder and surface the ones whose natural-language trigger rules fire today.
- Archive & collapse — retire stale material, fold redundant repetitions together.

What a librarian does is scope-dependent — it reads that scope's ontology, the user's preferences, and the exfu defaults to determine its behaviour.

**Librarian definition format:** TBD. The key constraint is that the definition must be rich enough for a platform-scheduled agent (e.g. a Claude scheduled task) to read it cold and know what to do, but not so procedural that it becomes a brittle script. Likely a markdown file with natural-language instructions (consistent with how reminders work), but the exact schema is an implementation decision.

### The nightly index

A special, exfu-owned librarian. Every night, it walks the entire substrate and regenerates a top-level **index** — a map of every scope, where it sits in the tree, which folder-types are populated, what their status is (data-bearing, pointer-only, empty), and the collapsed ontology set per scope. The index lives under `exfu/` as generated output (never hand-edited).

The index serves two consumers:
1. **The next day's agent.** Instead of grepping the filesystem, the agent reads the index and knows immediately what scopes exist, where they are, and what's in them. Fast orientation, even when the substrate is large or on Box with offline-caching issues.
2. **The substrate visualisation** (see below).

### Substrate visualisation

A first-class deliverable. An **HTML page** that renders the nightly index into a visual map of the user's entire substrate. The user opens it in a browser and sees:

- The full scope tree — nesting, grouping folders vs real scopes.
- For each scope: which folder-types exist, which are populated vs empty vs pointer-only.
- The ontology chain: what definitions are in play for any given scope.
- Librarian status: what's defined, when each last ran.

The visualisation is **read from the index, not by walking the filesystem live**. This means it's fast, works offline, and works even when Box has caching issues. The index is the single source of truth; the visualisation is a render of it. The HTML is generated as part of the nightly index run or on-demand.

The target audience is non-technical users. The visualisation must be self-explanatory without requiring understanding of the folder structure, file conventions, or any ExFu internal vocabulary.

### Data rules

Simple:

- **Only true secrets are banned.** Keys, tokens, passwords, API keys, credential files (.env, *.key, *.pem, credentials.json, id_rsa, id_ed25519) never enter the substrate. This is a hard constraint, enforced by agents and by git-sync ignore patterns.
- **Everything else is data.** Names, contacts, org charts, CRM records, personal notes, meeting minutes, preference profiles — all of it lives wherever it naturally belongs in the scope structure. There is no separate PII layer, no two-layer boundary, no special PII machinery.
- **Destructive operations require confirmation.** Deleting, overwriting, or moving scope-level structures requires explicit user confirmation. Standard from v0.1.0.

### Trade-offs being made

- **Uniform scope vs typed top-level folders.** v0.2.0's `orgs/`, `teams/`, `scopes/` express organisational meaning structurally. v0.3.0 collapses them into one concept, which loses the "I can glance at top-level and see which are orgs vs teams" affordance. The trade: structural simplicity, one set of conventions to learn, one pattern for agents to follow. Org-ness and team-ness move to the scope's ontology and context, where they belong (they're semantic properties, not structural ones).
- **Dropping the PII layer.** v0.2.0's two-layer model was designed for regulated team environments. Removing it means PII lives in the substrate alongside everything else. The trade: vastly simpler for the majority of users (solo founders, small teams) who just need to store contacts and notes. Regulated environments that genuinely need PII separation can implement it via their scope's storage backend and access controls — the substrate doesn't prevent it, it just doesn't mandate it.
- **Folder-type catalogue up front.** Defining nine standard folder types is more opinionated than v0.2.0's minimal conventions (`context/` hard, everything else soft). The trade: agents always know where to look, the inbox/reminders/todo distinction is clear from day one, and users don't reinvent the wheel per scope. The catalogue is open, so nothing is locked out.
- **Recursive scopes/nesting.** Nesting adds depth. A scope three levels deep has a longer parent chain to walk. The trade: it mirrors real organisational structure naturally (company → department → project) and the nightly index collapses everything for fast agent orientation. Flat is still possible — users who don't want nesting just don't nest.

## What — deliverables

This is a design doc. Implementation is a separate step. The deliverables below define *what needs to exist*, not the implementation order.

### 1. This design document
`plugin/planning/v0.3.0-substrate-revision.md` — the durable anchor.

### 2. ExFu base ontology
The canonical definitions that ship in `exfu/ontology/`. At minimum:
- What a scope is (and what a grouping folder is).
- What `scope.md` is and what it contains.
- What each folder-type in the catalogue means and how it behaves by default.
- What a librarian is.
- What the nightly index is.
- The `agent.md` / `readme.md` convention.
- The store-or-point principle.
- The secrets-only data rule.
- The explicit-upward-references principle.

### 3. Revised substrate skill
Implements the new structural conventions: scope detection (via `scope.md`), parent-chain walking, folder-type discovery, ontology loading, index reading. Replaces the v0.2.0 `orgs/`/`teams/` awareness with uniform scope awareness.

### 4. Revised install skills
All three install conversations (solo, team, team-admin) updated to scaffold the new structure: `exfu/`, `user/`, `scopes/`, `scope.md` files, the base ontology, and the nightly index librarian.

### 5. Nightly index librarian
The exfu-owned librarian definition + the index generation script. Walks the substrate, produces the index under `exfu/`. Must be installable as a platform scheduled task (Claude Cowork, etc.).

### 6. Substrate visualisation
An HTML page (generated from the index) that gives non-technical users a visual map of their substrate. Scope tree, folder-type status, ontology chain, librarian status.

### 7. Migration guidance
A note (or skill) covering how an existing v0.2.0 substrate maps onto v0.3.0:
- `orgs/<name>/` → a scope under `scopes/` with org-ness expressed in its ontology/context.
- `teams/<name>/` → a scope under `scopes/` with team-ness expressed in its ontology/context.
- Personal top-level `context/`, `databases/` etc. → content inside the `user/` special scope.
- The v0.2.0 PII layer is no longer required. Existing PII-layer data can migrate into the relevant scope's `databases/` or `context/`, or remain external if the user prefers.
- Existing per-user generated skills (`<username>-inbox`, etc.) continue to work as skills in the relevant scope's `skills/` folder.

### 8. Revised substrate-guide and primer
`substrate-guide.md` and `the-substrate-primer.md` updated to reflect the new model.

### 9. Teaching artefacts
Diagrams updated to reflect the new model. At minimum, the substrate-overview diagram needs to show the scope-based structure.

## Open questions

### Resolved in this revision
- **Multiple structural concepts for the same thing.** Resolved: one concept (the scope).
- **PII complexity.** Resolved: secrets-only ban, no PII machinery.
- **Agent discovery.** Resolved: uniform scope shape + folder-type catalogue + nightly index.
- **Maintenance agent conventions.** Resolved: librarians.
- **No visual overview.** Resolved: substrate visualisation (HTML, from the index).

### Still open

1. **Storage backend per scope.** Different scopes will likely be shared differently — a team scope on git, a personal scope on Box, a client scope on a shared drive. The v0.2.0 model assumed one storage backend per substrate variant (Box for solo, git for teams). The uniform-scope model surfaces a harder question: can different scopes within the same substrate use different backends? This likely requires scopes to declare their storage backend (in `scope.md` or `context/`). The mechanical problem is real: you can't nest a Box shared folder inside a git repo cleanly. Symlinks are a possibility — the substrate root lives on local disk, and individual scopes symlink to Box/shared-drive locations. **Needs design work before implementation.**

2. **Team sharing mechanics.** Related to #1. A team scope is now just a scope under `scopes/`. Multi-user access (who can read/write, how changes propagate) is a function of the storage backend, not the scope structure. The scope model is ready; the sharing plumbing needs design. The non-techie verb vocabulary from v0.2.0 (save, share-for-review, check-for-updates, fix-clashes) likely still applies for git-backed team scopes.

3. **Librarian definition format.** The concept is clear; the file format is TBD. Key constraint: readable cold by a platform-scheduled agent. Likely markdown with natural-language instructions, but the schema needs pinning down during implementation.

4. **Visualisation scope and UX.** The deliverable is clear (HTML, from the index). The specific UX — tree view? card grid? interactive drill-down? — is an implementation decision. Should be designed with non-technical users as the primary audience.

5. **CLAUDE.md guard.** v0.2.0 introduced a CLAUDE.md guard file at the substrate root to prevent accidental use without the substrate skill. This concept carries forward but needs updating: the guard should reference the scope-based model and the `exfu/ontology/` as the orientation point.
