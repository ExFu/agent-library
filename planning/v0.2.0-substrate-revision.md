# v0.2.0 — Substrate revision

Planning doc for the v0.2.0 plugin release. Captures the substrate-model evolution from the v0.1.0 substrate-guide (current `version: 4`) to the next revision.

This document is universal — no client-specific naming, no specific git provider named. It anchors back to: `T1-overview.md`, `cross-cut-storage-architecture.md`, the existing `substrate-guide.md` (in `src/shared/resources/`).

**Status:** specification ready for implementation. Driven by real-world install pressure during the first paid team engagement.

---

## Why

The v0.1.0 substrate-guide (`version: 4`) was designed around solo use with optional team-shared folders inside `context/`. It works for solo and gets the team plugins shipped, but two structural limitations have surfaced when applied to a real team install:

1. **Access scoping is informal.** The current model says "access scope is determined by where things live and who has access, not by a rigid hierarchy." That's true and flexible, but in practice teams want clear boundaries between *org-wide* content (e.g. brand voice, broadly applicable policies) and *team-wide* content (e.g. a sales team's CRM taxonomy). With everything under `context/[flexible]/`, the boundary is by naming convention only.

2. **No PII boundary.** The substrate is designed to be shareable (and team-syncable via git). Customer PII in a versioned shared repo is durable, replicable, and escapable — wrong threat model. v0.1.0 has no convention for separating PII-bearing data from shareable substrate content.

A third pressure, surfaced in the same engagement: **the v0.1.0 install assumes one team per user.** Multi-team membership was explicitly out-of-scope for v0.1.0 (open question in `T2-team-plugin.md`). For consultants and managers spanning departments, this is the immediate next limitation to remove.

The revision below addresses all three, while keeping v0.1.0 solo users untouched (the personal-default top-level layout is unchanged).

## How

### Principles

- **Additive, not migration-forcing.** The v0.1.0 top-level layout (`context/`, `databases/`, `scratch/`, `scopes/`, `_meta/`, `_trash/`) is preserved as the *personal default*. Solo users see no change. Team mode adds new sibling folders alongside the personal default.
- **Folders reflect types, not org hierarchy.** The substrate skill knows the conventions; the layout is for Claude to navigate, not for humans to mirror their org chart.
- **One canonical home per type.** Scopes live in top-level `scopes/` regardless of who owns them. Cross-references via metadata, not hierarchy traversal.
- **Hard conventions only where misuse is likely.** Most folder conventions are soft (created when needed). `context/` inside org/team/scope folders is the one hard convention — it stops users dumping context-shaped content into folder roots.
- **PII never persisted in shareable substrate.** The substrate is for shareable knowledge; PII is held separately, behind access control. Claude reads PII at runtime; the substrate doesn't store it.
- **Universal vocabulary in the plugin.** No specific git provider named in plugin docs (clients use various — GitHub, Bitbucket, Gitea, etc.); no client-specific examples; user-facing language uses the parts (knowledge base, skills, tools, things on a timer).

### The two-layer model

The substrate is conceptually two layers:

**Layer 1 — Substrate proper (file-based, git or Box).** Holds: skills, templates, context docs (brand voice, policies, conventions), structured non-PII data, configuration, sanitised test fixtures. Versioned, auditable, shareable, evolves slowly. Reps interact through Claude using non-techie verbs (see below). Reps never see git commands.

**Layer 2 — PII layer (access-controlled store).** Holds: anything containing identifiable PII — customer profiles, drafting feedback diffs, per-customer working memory. Implementation is typically a small access-controlled database (e.g. Postgres) accessed via a guarded MCP connector. Skills in Layer 1 talk to Layer 2 through the connector. The connector enforces access control — every query parameterised by `(user_id, subject_id)`, no general SELECT, no admin verbs from the rep-side connector.

**Why split:** PII in versioned shared substrate is durable, replicable, escapable — wrong threat model. PII at runtime is unavoidable (Claude has to read emails to do its job; emails contain PII). The substrate's job is *persistence*; the boundary is what gets *stored*, not what Claude *sees*. This split also matches the typical shape of accompanying systems (CRMs, customer DBs) — the substrate fills the gap when there's no dedicated tool, but doesn't compete with one.

### Substrate structure (folders as types)

Top-level layout:

```
[root]/
  CLAUDE.md             # guard against accidental mounts
  _meta/                # system infrastructure
  _trash/               # soft-delete (60-day recovery)
  context/              # default/personal context (read to orient)
  databases/            # default/personal databases
  scratch/              # ephemeral — TOP-LEVEL ONLY
  scopes/               # ALL scopes — TOP-LEVEL ONLY
    <scope-name>/
      context/          # HARD convention
      planning/         # soft
      generated/        # soft
      databases/        # soft
      README.md         # YAML front-matter linking to org/team
  orgs/                 # one entry per org (only if user is in one or more orgs)
    <org-name>/
      context/          # HARD
      databases/        # soft
      README.md
  teams/                # one entry per team (only if user is on one or more teams)
    <team-name>/
      context/          # HARD
      databases/        # soft
      README.md         # YAML front-matter: parent_org
```

Conventions:
- `context/` is the only HARD convention inside `orgs/<org>/`, `teams/<team>/`, `scopes/<scope>/`.
- `scopes/` is top-level only. ALL scopes live there regardless of ownership; org/team membership is metadata in front-matter.
- `scratch/` is top-level only. Stops Claude dumping into root.
- `planning/` and `generated/` are scope-folder conventions only.
- Skills + scheduled-tasks are install-time deliverables — folders only created when there's actually something to deliver. Runtime homes are `~/.claude/`.
- Cross-linking via Obsidian-style YAML front-matter: scope's README has `team: <team-name>`, `org: <org-name>`. Team's README has `parent_org: <org-name>`.

**Why top-level scopes:** to find "scopes for team X", Claude searches `scopes/` filtered by `team: X` in front-matter. No hierarchy traversal. One canonical home, regardless of ownership. Searches and migrations are simpler. Org/team membership can change without moving files.

**Why personal-default at top-level:** solo users see the same layout as v0.1.0 / substrate-guide v4. Team mode is purely additive — `orgs/` and `teams/` appear as siblings if the user is in one or more orgs/teams. Existing solo users don't migrate.

### Multi-org / multi-team support

The install conversation asks the user whether they're in zero, one, or multiple orgs/teams. The folder structure naturally accommodates any of these — multiple entries under `orgs/` and `teams/` work without further adaptation.

This addresses the v0.1.0 open question (`T2-team-plugin.md`): *"A user on two teams (e.g. a manager spanning departments) needs two team substrates. Out of scope for v1; the team plugin assumes one team."*

In v0.2.0, this is no longer out of scope.

### CLAUDE.md guard file

A file at the substrate root that prevents accidental treatment of the substrate as a generic working folder when it's mounted in a Claude session without the substrate skill loaded. Content (canonical, ships in `src/shared/resources/` for install skills to reference):

```
# Don't use this folder

This is a substrate root.

Do not read, write, or otherwise interact with the contents of this folder
unless your session has loaded the substrate skill (or a derivative
that knows the substrate conventions).

If you've accidentally been pointed here, stop and ask the user to either:
- Load the appropriate substrate skill, or
- Work in a different location.

This protects the substrate from being treated as a generic working folder.
```

### Non-techie verb vocabulary (for git-backed team substrates)

Reps speak natural verbs to Claude in place of git terms. The substrate skill maps to git provider API calls.

| Rep says | Skill does |
|---|---|
| save | commit on personal branch |
| share for review | push branch + open PR via git provider API |
| check for updates | pull from main |
| fix clashes | guided merge conflict resolution |
| approve change | merge PR (owners only) |

Dropped from the natural vocabulary: branch / draft space / sandbox (too technical), fetch (use pull — the difference is outwith non-techie purview), diff / show my changes (not user-facing for non-techies).

### Permission-aware substrate skill

A single skill, no separate team-admin substrate skill. On load:

1. Skill asks the git provider's API "what permissions does this user have on this repo?"
2. If user has admin/maintainer rights → surface review/approve/reject verbs.
3. If not → only surface save/share-for-review/check-for-updates.

Git provider's permission model is the gatekeeper. No separate Claude-side permission scaffolding. Review and merge happen IN Claude (not via web UI — Claude can't drive web UIs without a browser-control extension, which is outside v0.2.0 scope).

Future revisions: owner-notification flow when a PR opens; semantic review of skill changes (the genuinely hard problem); auto-merge for low-risk changes.

### Lightweight sync mechanism

For team git substrates, syncing defaults to a non-LLM script that pings the team git remote for HEAD commit hash, compares to local, and only fires Claude when there's actually a delta. Tokens-only-when-needed. Even if wrapped in a scheduled Claude task, the LLM wakes only on confirmed delta.

### Trade-offs being made

- **Adding hierarchy vs flat structure.** v0.1.0's flat `context/[flexible]/` is simpler but blurs access boundaries. v0.2.0 adds typed top-level folders (`orgs/`, `teams/`) — slight structural complexity, much clearer access scoping.
- **Top-level scopes vs nested-by-owner.** All scopes top-level looks like everyone's scopes pile up in one place; using metadata for ownership keeps search simple. Trade-off: scope folders won't cluster visually by owner. Counter: humans don't browse scope folders directly — Claude does.
- **PII layer adds operational complexity.** A connector + database is more setup than "just files in git". But the alternative is leaking PII into version control. There's no third option that's both simple and safe.
- **Universal naming in plugin docs vs concrete examples.** Universal docs are dryer; concrete examples are clearer but client-specific. We pay the dryness cost so the plugin remains genuinely reusable.

## Open questions

- **Migration path for existing v0.1.0 solo users.** The personal-default top-level layout is preserved, so most users won't need to migrate. Worth verifying with explicit migration-check logic in `exfu-migrate-from-fetch-model` or a new sibling skill.
- **PII layer reference implementation.** v0.2.0 ships the principle and guidance. Should it also ship a reference MCP connector skeleton (e.g. minimal Postgres CRUD) that clients can adapt? Or stay framework-agnostic? Real-world install (the first paid team engagement) will surface a usable concrete implementation that could be generalised back into the plugin.
- **Read-only mode for restricted joiners** (still open from v0.1.0).
- **Mobile + scheduled tasks under git** (still open from v0.1.0).
- **Skill-sync mechanism for non-git substrates.** v0.2.0 above covers git-backed team substrates. Box-backed solo and Box-backed team substrates need their own sync pattern. Scope decision pending.
